MAJOR DECISION 1: How to disable scaling?
Options Considered:
  A) Add conditional branches throughout codebase (if apply_scaling: scale...)
  B) Set scale factors to 1.0 (identity scaling)
  C) Skip _compute_scales() call entirely

Choice: B (Identity scaling)
Reasoning:
  - Pro: Keeps code path consistent, no new branches
  - Pro: Same mathematical result (x/1.0 = x)
  - Pro: Logging still shows "before/after" for debugging
  - Con: Tiny computational overhead (unnecessary division)
  - Verdict: Clarity and maintainability > micro-optimization

💡 INSIGHTS & PATTERNS DISCOVERED
================================================================================

1. ARCHITECTURAL PATTERN: Dual Scaling Approaches Coexistence
   Observation: The codebase has both old (MaxAbsScaleTarget/Channels) and
   new (computed scales in model graph) approaches

   Implication: Backward compatibility layer exists for gradual migration
   Learning: Legacy code doesn't disappear overnight; good design supports
   multiple approaches during transition periods

2. DESIGN PATTERN: Data Transformation in Model Graph
   Observation: Scaling happens INSIDE PyMC model graph, not preprocessing

   Why This Matters:
   - Scales are pm.Data (can be updated for predictions)
   - Transformations are part of computational graph
   - Enables proper derivative computation

   Learning: In probabilistic programming, keep transformations in the graph
   when possible for automatic differentiation

3. PYDANTIC PATTERN: validate_call Decorator
   Observation: __init__ decorated with @validate_call

   Implication: Parameter validation happens automatically
   Learning: Type hints + Field() + validate_call = robust API
   Benefit: Don't need manual type checking, Pydantic handles it

4. LOGGING PATTERN: Singleton Logger
   Observation: Custom _SingletonMMMLogger class prevents log duplication

   Why This Exists:
   - Multiple MMM instances would create multiple handlers
   - Leads to duplicate log messages

   Learning: When classes are instantiated multiple times, use singleton
   pattern for loggers to prevent handler accumulation

5. SERIALIZATION PATTERN: JSON for Metadata
   Observation: All attrs stored as json.dumps(value)

   Why: NetCDF format (InferenceData storage) requires string values
   Learning: When dealing with file formats, understand their constraints
   JSON is a universal serialization format for metadata

6. CODE ORGANIZATION PATTERN: Mixin Inheritance
   Observation: MMM inherits from MaxAbsScaleTarget, MaxAbsScaleChannels, etc.

   Learning: Mixins provide modular functionality composition
   Trade-off: More flexible but harder to trace behavior (multiple inheritance)

7. TESTING PATTERN: Suppress Logging During Tests
   Implementation: logging.getLogger(...).setLevel(logging.CRITICAL)

   Why: Test output clarity vs. debugging information
   Learning: Different contexts need different log levels; make it configurable
